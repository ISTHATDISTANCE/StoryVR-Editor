# StoryVR authoring app

This app runs the one-story StoryVR authoring workflow from a prepared resource folder.

Normalize an existing capture when needed:

```sh
npm run storyvr:story -- --resource-folder <story-slug>/captures/active
```

Then launch the authoring UI from that prepared folder:

```sh
npm run storyvr:author -- --resource-folder <story-slug>/captures/active
```

Alternative when the story follows the workspace convention:

```sh
npm run storyvr:author -- --story-folder <story-slug>
```

The app writes all authoring state into the story container:

- `<story-slug>/analysis/storyvr/project.json`
- `<story-slug>/analysis/storyvr/story-graph.json`
- `<story-slug>/analysis/storyvr/story-canvas-segments.json` (generated semantic progress navigation)
- `<story-slug>/analysis/storyvr/environment-search-recommendation.json`
- `<story-slug>/analysis/storyvr/performance-optimization.json`
- `<story-slug>/analysis/storyvr/procedural-dynamics.json`
- `<story-slug>/analysis/storyvr/source-motion-overrides.json`
- `<story-slug>/analysis/storyvr/source-motion-playback.json` (optional declarative shared-timeline contract)
- `<story-slug>/analysis/storyvr/proposals/*.json`
- `<story-slug>/analysis/storyvr/decisions/*.json`
- `<story-slug>/webxr-adaptation/public/environment-enhancement/*` (author-uploaded surroundings)
- `<story-slug>/discovery/storyvr-runtime.json`
- `<story-slug>/dist-webxr-adaptation/` (production reader rebuilt by Compile)

## Workflow

1. Prepare one source story folder, usually `<story-slug>/captures/active`, and normalize it with `storyvr:story` when needed.
2. Start `storyvr:author` with that resource folder.
3. Review and edit `Source Graph`.

   Whenever a StoryVR project opens, including an existing story, StoryVR checks for `analysis/storyvr/story-canvas-segments.json`. If the grouping is missing or stale, StoryVR asks the signed-in Codex CLI in the background to organize the saved story into two to seven semantic sections and writes that file; this check does not depend on Source Graph being the currently restored checkpoint. The progress strip remains navigation above one continuous Source Graph canvas: it never filters, groups, rewrites, or recompiles the underlying beat/variant chain. Each section must contain one contiguous beat range, and the sections must cover every authored beat exactly once in story order.

   StoryVR signs both the ordered beat structure and the narrative inputs used for grouping, including titles, text, variants, and explicit arrows. A relevant draft edit immediately marks progress as waiting for save. After `Save story order`, StoryVR runs an asynchronous incremental update that supplies the previous sections, a compact complete outline, and detailed context only for changed beats, variants, and their neighbors. Cached current results return without invoking Codex. Concurrent requests for the same saved flow share one job, and a result is committed atomically only if its signature still matches the saved graph. Invalid, stale, failed, or malformed output never changes the story canvas or overwrites the last saved grouping.

4. Compose the story world in order:
   `Spatial Relations`, `Environment Enhancement`, `Attention Guidance`.

   `Spatial Relations` is the second visible StoryVR checkpoint and incorporates Asset Topology. It opens on a full-width Story Canvas rather than a separate topology option workspace. Selecting a beat or variant card opens that card's scene in the Spatial editor; closing the editor flushes the spatial draft and returns to the canvas. The Spatial canvas intentionally has no Asset Library because its scene membership comes from the links already saved in Source Graph.

   Each scene starts from one deterministic inferred layout containing only the assets linked to that beat or variant. The editor does not generate alternative layout or viewpoint options; authors directly move, rotate, scale, copy, and paste the inferred scene objects. The reader position is represented only by the scene’s concrete Reader transform. Manual changes write concrete transforms into the active scene and participate in the same persistent undo/redo history. There is no separate topology preview or `Active species` view.

   `Environment Enhancement` offers `Search` and `Generate` tabs rather than an AI design-option bundle. Search analyzes every saved story beat to recommend editable keywords, then looks only for 360° equirectangular HDRIs from Poly Haven and ambientCG; cards link to each provider's original source page, and StoryVR does not download provider images or request provider access tokens. Generate uses the signed-in Codex CLI to create one story-local 2:1 equirectangular LDR `.png` panorama from an editable prompt. Authors can also paste, drop, or choose up to four PNG, JPEG, or WebP screenshots and image files as temporary visual references; StoryVR verifies their file signatures and asks Codex to extrapolate their setting, layout, materials, lighting, and mood into the full 360° sphere. Generate and manual `.hdr` / `.exr` upload also send the resulting panorama to the signed-in Codex CLI as a visual reference for a square, tileable matching-ground texture. StoryVR installs the panorama and ground atomically, keeps the panorama unchanged as the surrounding, and uses the generated texture only on the editable world-fixed near-ground movement cue. A generated or uploaded pair is assigned only to the currently open beat by default; `Apply to other beats…` can reuse that same asset pair and tuning on an explicit checklist of other beats without duplicating files or rerunning generation. Beat-scoped environments are previewed, tuned, and compiled into the reader through base-relative runtime paths. Unassigned beats use StoryVR's standard neutral scene, while legacy story-wide drafts remain readable as the default environment until an author creates beat-specific overrides.

   `Attention Guidance` opens the same beat-and-variant canvas pattern after Environment Enhancement. For each beat or variant scene, StoryVR independently derives a runtime target set from direct JS/Three.js model, part, animation, and visibility changes and a semantic target set from the saved beat text, exact Source Graph links, asset labels, and named-part metadata. Variant runtime evidence remains scoped to the option that produced it; an unavailable capture or a DOM/preload link is not relabeled as direct runtime evidence. Semantic ranking is confidence- and margin-gated so generic text does not silently choose among several plausible GLBs.

   The two channels are reconciled internally as `confirmed`, parent/part `compatible`, provisional `runtime-only` or `semantic-only`, `conflict`, or `unresolved`. One-sided and conflicting results are retained in the inference contract instead of being discarded or silently overridden, while the authoring UI directly accepts the suggested target set without showing channel evidence, reconciliation labels, or a separate review action. Selecting a card loads its composed Spatial Relations scene and validates every reconciled candidate against live, nonempty visible GLB geometry before creating an authoring-only sphere. Exact active-part selectors and safe standalone GLBs are supported; automatic inference does not fall back to broad groups, hidden controls, ambiguous shared-timeline models, or camera focus. A scene with no inferred target starts with no sphere, but the author may explicitly select a visible saved-scene GLB—including a shared-timeline model—to add one; the server rejects arbitrary or out-of-scene asset IDs. Authors can translate and reset validated spheres but cannot rotate, scale, delete, or use them as story objects.

   Compile removes the authoring spheres and emits only finite, evaluated attention targets plus a versioned reader cue policy. Until the distance from the active desktop or WebXR viewer to a resolved target's visible bounds first reaches 3 meters, the target receives a soft, steady additive glow overlay and, only while those bounds are outside the active view frustum, a camera-edge arrow points toward it. Entering the 3-meter radius permanently completes that target for the current story session: both cues disappear immediately and do not return after the reader moves away, changes beats or variants, or leaves and re-enters WebXR. The reader never substitutes a sphere, origin marker, arrow, or glow when the referenced GLB or exact part is missing, hidden, or unresolved.

   `Spatial Relations` is the canonical `spatial-relations` checkpoint. When the checkpoint first becomes ready, StoryVR infers one default scene for each authored beat and variant, records the inference inputs and confidence, and displays those scene states on the Story Canvas. GLB and image entities are identified by stable source asset plus scene identity rather than transient Three.js UUIDs, GLB node names, or child indexes. Reader text is a hand-attached runtime surface and is not displayed or transformed in this checkpoint.

   Legacy text-panel placement metadata remains readable for older saved projects, but it no longer participates in Spatial Relations rendering, transforms, or travel inference. Asset transforms are scene-scoped additive overrides, so the same linked asset can use a different layout in different beats without rewriting its internal meshes, bones, materials, or animation tracks.

   An accepted `storyvr-source-spatial-composition/v1` is handled as one source-identified assembly only in the beats where its exact active set applies. StoryVR keeps every member's source matrix immutable as its reset baseline, exposes an editable assembly root with its exact editable members folded beneath it in the object hierarchy, and renders only the declared active members. A source-configuration assembly is framed once from its combined persistent-member bounds, while older reference-local assemblies retain anchor framing; neither path independently normalizes child GLBs. Authors may move, rotate, or resize the whole assembly or any individual member; a manual member transform stays associated with the assembly and takes precedence over that member's captured starting transform until Reset restores it. Ordinary thumbnails and unrelated scene assets stay available to the fallback path but cannot cover the accepted composition. A pre-existing ordinary manual GLB transform or authored copy still blocks automatic composition promotion and returns that scene to ordinary review. The compiled Reader uses the same assembly contract and adds a neutral reflection only to a fully metallic, texture-bearing framing anchor when no authored environment exists, without modifying the source material or any unrelated model.

   The Spatial Relations editor lets the author select the beat-owned Reader pose plus the active scene's linked GLB roots and image planes. In the object list, Shift-click selects a contiguous range and Command/Ctrl-click adds or removes one object; a multi-selection moves, rotates, or scales around one shared center while preserving every member's relative transform. The Reader can move and rotate but cannot scale, so any selection containing the Reader keeps group scaling unavailable; its position and facing are shared by that beat's within-beat variants. A manual Reader edit overrides the live source-camera fallback until Reset restores inference. GLBs and images can move, rotate, or scale with the same viewport gizmos and numeric controls. Manual edits remain distinct from the inferred baseline, support reset-to-inference, and are saved with stable scene-scoped entity IDs. Each asset uses an additive author-transform wrapper outside its normalized and animated content root, so authored placement composes with source clips, shared timelines, material bindings, and later interactions without animation ticks resetting the edit. Spatial Relations v1/v2 authored GLBs migrate to the current floor-contact pivot before their transform is reused; v3 persists that placement basis with cross-scene transform propagation. Final Review and the reader resolve the same per-beat visual-asset and Reader-pose composition used by the checkpoint preview.

   Compile emits the current saved `spatialRelations` contract and resolved per-beat/variant scenes into the runtime payload. Loading older projects migrates legacy story-wide GLB transforms into every beat that links the asset, preserves compatible `text-comfort` placement data, and leaves the migrated Spatial Relations decision as a draft for review. The reader retains fallbacks for legacy global Spatial Relations and `textComfort` runtime payloads. Asset Topology remains only as a derived compatibility projection for older downstream consumers; it is not a separate authoring checkpoint.

   Shared-timeline anchors are declarative and story-local. An anchor is active by default and needs a normalized `localProgress`; an anchor with `presence: "inactive"` (or `entryMode: "inactive"`) clears that asset without a progress value. A model may opt into floor alignment with `framing.verticalAlignment: "ground"`; omitted framing keeps the existing centered reader placement. This supports sequential shared-timeline assets and later re-initialization without story-name, beat-index, clip-name, or node-name logic in the engine, preview, or reader. Invalid schema versions, asset references, anchors, loop modes, timelines, and clip declarations are returned as nonfatal `sourceMotionPlayback.diagnostics` instead of silently selecting legacy playback.

   Shared-timeline material behavior is also declarative. An asset can declare reusable `materials` recipes such as `texture-background-fade`, `uv-stripe-flow`, `texture-atlas-scalar-field`, or `layered-texture-atlas-scalar-field`, then connect GLB node properties, timeline progress/time, wall-clock time, or constants to recipe uniforms through `material-uniform` bindings. The background-fade recipe mixes an existing texture with a declared background color while a driver controls both texture contribution and opacity. The layered-atlas recipe accepts the atlas column/row counts, sample count, data channel, scalar gain, alpha floor, color ramp, and normalized atlas offset as story-local parameters; `sliceY` selects and interpolates a layer while `showAmt` controls its animated contribution. Static render settings such as sidedness, transparency, depth writing, blending, and render order stay in the story-local recipe. Use `visibility` when a driver should only gate a renderable; reserve `draw-range` for geometry whose index order genuinely represents reveal order. The authoring preview and compiled reader evaluate the same recipe and binding contract.

   Point-cloud companions are likewise optional and declarative. StoryVR activates one only when the imported runtime contains a valid `storyvr-pointcloud-composite-effect/v1` record scoped to `explicit-source-ptcloud-link-only`; a standalone `.pcd` asset does nothing. The shared author/reader loader attaches the PCD only to its explicitly matched GLB, decodes bounded ASCII PCD groups, preserves the captured model-to-cloud transform, and drives each fixed droplet layer from its named source animation node with a timeline fallback. A missing or invalid companion is reported nonfatally and never prevents the GLB or the rest of the story from rendering. Ordinary stories retain their prior runtime, graph, checkpoint, and reader behavior.
5. Review the story behavior in order:
   `Dynamics`, `Transition`. These checkpoints do not generate design-option bundles. After Attention Guidance is saved, they prepare draft previews of source behavior already attached to the Source Graph in the composed environment and spatial layout; the author saves Dynamics and then Transition explicitly before Interaction Control becomes available. Dynamics opens on a full-width Story Canvas containing every authored beat and variant; selecting a card opens the exact saved scene with its beat-resolved environment, classification evidence, playback controls, and manual motion-link editor. The reader-hand text system surface is intentionally not materialized in this scene editor.

   In that exact beat or variant scene, the author may also describe the intended scene motion in plain language—for example, “Have several sharks swim in slow, staggered circles around the reader, using the animated shark models and hiding the static copies.” Codex returns a declarative scene-patch candidate rather than executable code. The candidate may select existing GLBs and embedded clips from the story-wide asset library, propose exact scene-local asset-link changes, project the resulting Spatial Relations scene, hide authored template models, and choose a bounded school-orbit or waypoint loop with clamped instance, timing, orientation, and comfort values. It cannot return executable code, URLs, arbitrary external assets, or unbounded geometry.

   `Generate preview` and `Regenerate preview` keep the complete asset, layout, visibility, and motion patch local to the browser. The author preview shows the projected scene plus a before/after impact summary; no Source Graph, Spatial Relations, or Dynamics artifact changes until the author selects `Apply scene changes & motion`. Apply revalidates the preview's graph, spatial, asset-inventory, and procedural baselines, then commits the exact-scene asset override, projected Spatial Relations contract, and motion plan together as one persistent Undo action. Unrelated beats, variants, and manual transforms remain unchanged. Applied procedural motion is stored separately from animation-probe-derived `sourceDynamics`, can be removed without changing source motion links, and is anchored to the authored reader-start world pose rather than following the headset. The shared author and reader sampler applies deterministic staggering to any number of existing scene model instances, while minimum distance, maximum speed, and fade-in behavior remain comfort-clamped.

   Closing the scene saves dirty motion-link assignments through the existing source-motion API and returns to the same canvas position. Its derived draft refreshes automatically from the saved Source Graph and upstream composition, while `Save checkpoint` confirms both reviewed source behavior and applied procedural plans; variants retain their host beat's individual non-camera clip assignment rather than introducing a second per-variant source-motion schema. Transition uses the same canvas-first workflow and explicit checkpoint save, but its original default and parallel variant cards are read-only. Every beat-to-beat and variant-to-variant arrow uses the same binary presentation: an edge with no matched GLB animation shows only `No mapped transition`, while a matched edge shows a text-free looping GLB thumbnail. Selecting any mapped thumbnail opens the existing full spatial Transition preview and starts the mapped animation immediately. Same-beat variant edges reuse the destination variant's exact mapped Dynamics clips without adding unsupported same-beat records to the beat-pair motion-assignment schema. Closing the preview saves dirty host-beat assignments through the existing source-motion API and restores the canvas position. Transition prefers an optional asset-level `source-motion-playback.json` contract: authored beats resolve to inactive, initial, animated, or held states on one source-local timeline, and every coordinated clip—including the declared source camera—is evaluated on one absolute mixer clock. Per-track assignments remain semantic contributor metadata and do not select primary preview playback. Stories without a shared-timeline contract retain the mapped legacy per-track fallback. Manual Source Graph asset-to-beat links remain authoritative for probe inference and later-checkpoint invalidation.
6. Review the reader experience in order:
   `Interaction Control`, `Final Review`. Interaction Control is proposal-free: it derives its editable boundary structure directly from the current Source Graph, saved Spatial Relations, and reviewed Transition. It opens on a full-width Story Canvas that preserves every beat, parallel variant card, and variant link. Selecting a beat or variant card opens its exact Spatial Relations scene as an in-beat interaction editor. The author can click visible GLB geometry in the scene or use the synchronized target list to mark a whole GLB or its deepest safe named/indexed part as one-hand grabbable, two-hand scalable, or both. Optional parent-local movement, rotation, and scale ranges use simultaneous translucent clones of that exact target: teal is Minimum and orange is Maximum. Clicking either ghost or its matching row activates the gizmo for that endpoint, and movement limits also draw the box between both endpoints.

   Sequential boundaries with `No mapped transition` use `Controller button press` by default; mapped transitions remain `Unassigned` until the author chooses a control. `Direct manipulation` is available only when the exact source scene contains at least one authored in-beat interactable, and its destination list contains only those interactables. For each selected target, the author chooses one or more completion-trigger components from the transforms that its affordances can produce: position, rotation, scale, or any supported combination. Only those selected components must reach their destinations and remain inside their authored transform ranges; unreachable destinations are marked in the editor. Existing records without an explicit trigger-component list continue to require every affordance-supported component. The controller icon above the Story Canvas opens one shared mapping that automatically applies to every current or later `Controller button press` transition; arrow icons no longer open an individual controller editor. Controller navigation may use face buttons, Menu, thumbstick press, or thumbstick directions. Thumbstick directions additionally expose direction-only VR locomotion actions. By default, Left Up/Down moves continuously forward/backward, Left Left/Right strafes continuously, Right Left/Right turns in 45-degree snaps, Right Up activates free teleport, and Right Down turns back 180 degrees. Locomotion actions cannot be assigned to face buttons, Menu, or thumbstick Press. Trigger and Grip are omitted from the authoring controls; Trigger belongs to the UI-ray interactor for click and scroll, while Grip belongs to panel and scene-object grabbing. Reset restores `Controller button press` on an unmapped boundary and clears the assignment on a mapped boundary. Closing an editor keeps the shared controller mapping and any route-local Direct or Reader locomotion assignments, then restores the canvas position; `Save checkpoint` remains the only persistence boundary and is disabled while a mapped boundary is unassigned or a Direct destination is incomplete. Within-beat variants keep a separate `UI button press` contract and never become narrative branches. Previous and next buttons live on the reader's text panel and follow each variant group's saved order and wrap behavior. Text panels follow the reader's hand and never create hidden travel stations. `Reader locomotion` supports physical walking and boundary-driven virtual teleport modes, and older `Embodied progression` records remain readable as the legacy name for that locomotion family.

   In the compiled WebXR reader, the first authored Reader pose establishes story entry. Later separated Reader poses feed explicit physical-walking or virtual-teleport boundaries; this earlier boundary-driven virtual teleport advances the story to an authored destination and facing while preserving live headset tracking. Free controller teleport is separate: hold Right Up to aim, use the valid/invalid reticle to check the landing point, and release to teleport only when the reticle is valid. It is limited to the current scene's bounded, flat StoryVR ground plane, so it does not support stairs, multiple levels, arbitrary model surfaces, or points outside the ground bounds. Free teleport never changes the beat or satisfies a narrative boundary. Thumbstick movement is available throughout the story, including Direct manipulation and Reader locomotion boundaries: it preserves analog strength and diagonals, moves on the horizontal plane relative to live headset yaw, and applies 45-degree snap turns or a 180-degree turn back around the headset rather than the rig origin. The text panel attaches to the left hand by default. Aim at either the expanded panel or its minimized `Aa` state with the other hand, hold that controller's Grip to grab it, and release to attach it to that hand. When the ray is not on the panel, one Grip grabs an authored grabbable target and two Grips scale an authored scalable target; every frame clamps the target to its saved local transform ranges. Authors can opt a one-hand target into Elastic dragging: slow motion stays 1:1, while quick translation along the controller ray receives a smooth gain up to 4× so pulls reel a distant object closer and pushes send it farther away. The gained displacement and its 90 ms inertial response stay on the signed controller-ray axis instead of inheriting sideways hand motion. After easing into the gained velocity, the reader preserves it for as long as Grip remains held; releasing immediately pins the object instead of throwing it. Tracking discontinuities are rejected rather than amplified, and reaching an authored position constraint stops the inertial motion. A Direct transition advances only after its selected interactable destinations satisfy the capability-reachable channels. Trigger is exclusively the UI-ray action: it clicks minimize, restore, and variant buttons, and trigger-drag scrolls overflow panel text. Variant beats add Previous and Next UI buttons to the same panel so the reader can ray-click backward or forward through the variants. Reserved Trigger/Grip gestures cannot execute legacy authored mappings or move the story forward. Outside XR, both the compiled desktop panel and Final Review's spatial panel can be repositioned with a mouse; dragging the `Aa` state does not also restore it.

   Use `Final Review` to inspect the canonical reader preview composed from all current saved decisions, including the same mouse-drag and WebXR grip-grab behavior for the panel. Add a final tuning prompt when the reader story needs small output adjustments, save the final story, then use `Compile + optimize + build reader`. StoryVR compiles the current decisions into `<story-slug>/discovery/storyvr-runtime.json`, prepares the managed source in `<story-slug>/webxr-adaptation/`, applies the bounded performance profile, and runs the production Vite build into `<story-slug>/dist-webxr-adaptation/`. If a legacy reader has a `tools/build-story-instance.mjs` data generator, StoryVR runs it before Vite. The signed-in Codex CLI analyzes only a bounded summary of the story's renderable workload and selects validated desktop pixel-ratio, antialiasing, shadow, XR framebuffer-scale, and fixed-foveation settings. The applied profile is embedded in the runtime and recorded in `<story-slug>/analysis/storyvr/performance-optimization.json`.

   This pass cannot edit source files, assets, transforms, camera poses, timing, sequencing, text, or interactions. StoryVR clamps every numeric setting to the reader contract before applying it. If Codex is unavailable, unsigned, times out, or returns invalid JSON, the compiled reader remains usable with its existing render defaults and the compiler records a nonfatal diagnostic plus a skipped or failed audit report.

Each editable checkpoint has one `Save checkpoint` action and remains editable after saving. Later checkpoints wait until earlier decisions are saved and current. A material upstream edit changes that checkpoint back to a draft and marks affected downstream decisions stale until the author saves the updated chain. Regeneration preserves current upstream choices. `Spatial Relations`, `Dynamics`, `Transition`, and `Attention Guidance` do not generate design-option bundles; Spatial Relations starts each scene from one deterministic inference, while Environment Enhancement's Generate tab creates one paired panorama-and-ground environment.

Interactive preview metadata belongs in a screen-space overlay, not inside the Three.js story scene. Shared previews do not add ground circles, stage discs, halos, or other decorative geometry unless the author explicitly requests that geometry or the selected StoryVR option requires it.

## Undo and redo

StoryVR keeps one chronological authoring history for the current browser session. Use `Command-Z` on macOS or `Ctrl-Z` on Windows/Linux to undo; use `Command-Shift-Z`, `Ctrl-Shift-Z`, or `Ctrl-Y` to redo. The header buttons show the next operation available in each direction. When focus is inside an input, textarea, select, or editable element, the browser's native text undo takes precedence.

History includes draft edits, Source Graph operations and saves, motion-link saves, generated options, environment source selection, uploads, paired panorama-and-ground generation, attention-marker moves, graph regeneration, and checkpoint saves. It excludes navigation, search, filters, camera and playback controls, authentication, and Compile. Persistent redo restores the exact saved checkpoint rather than rerunning generation or re-uploading an asset. History keeps the latest 50 operations and is cleared by a page reload; its temporary checkpoints are not written into the story folder.

## AI engine

The preferred provider is the local Codex CLI auth boundary.

- The UI starts `codex login --device-auth`.
- The browser receives only the login URL, device code, and status text.
- Codex stores credentials in the local Codex CLI configuration.
- Proposal generation runs `codex exec --json` in read-only mode and asks Codex to return a structured proposal bundle for generated-option checkpoints.
- Source Graph progress generation runs asynchronously in an isolated temporary workspace. Its prompt contains the saved narrative outline and instructs Codex to use only that JSON input; Codex returns section ids, labels, and beat ids, while StoryVR supplies signatures and provenance after deterministic validation.
- Final compilation runs a separate read-only Codex performance-planning request after the runtime and reader source are prepared. The response is a small renderer profile, not code; StoryVR validates it, writes an audit artifact, and applies the profile through the compiled runtime.
- `Dynamics` and `Transition` continue to use the existing animation-probe judgment from the Source Graph rather than generating design-option bundles. Dynamics additionally offers an explicit scene-scoped natural-language action: Codex returns a JSON-only composite scene candidate constrained to the story's existing GLB inventory and clips. StoryVR canonicalizes its proposed exact-scene links, Spatial Relations, authored-model visibility, and procedural motion; the author must preview and apply that coordinated patch before any of it is persisted. Transition remains probe-derived.
- `Environment Enhancement` uses the signed-in Codex CLI to recommend search keywords from the complete saved story graph and, on the Generate tab, to create a 2:1 equirectangular LDR PNG from the author's editable prompt. It then uses that generated panorama—or an uploaded HDR/EXR panorama—as the visual reference for a square matching-ground texture. Generation and upload affect only the open beat; the author can explicitly apply the installed pair to any checklist of other beats. Public catalog search, manual HDR/EXR download/upload, deterministic asset validation, prompt review, beat assignment, and final checkpoint save remain separate author-controlled actions.
- `Spatial Relations` infers an editable transform baseline from the complete saved story graph and the actual preview geometry. Semantic evidence selects anchors and coordinate spaces; beat-scoped topology generation proposes layout families using only that scene's saved links, and deterministic geometric evaluation materializes their numeric transforms. It does not accept client-supplied asset IDs or ask an AI response to invent unchecked story-specific meter values.
- `Attention Guidance` derives narrow candidate links from the saved Source Graph, then lets the loaded authoring preview confirm a finite default position only when the referenced GLB model or part is visibly renderable. Unresolved candidates stay separate from confirmed markers and do not become zero-position placeholders.
- `Interaction Control` records hand-attached text panels as reader-relative system surfaces, so obsolete world-, asset-, or source-focus panel transforms cannot infer locomotion. Reader locomotion requires a separate explicit spatial route rather than hidden text-panel placement.
- Beats with preserved within-beat variant groups receive a separate `UI button press` Interaction Control record. The compiled reader renders previous and next controls on the text panel and swaps variant text/assets without advancing the narrative beat or turning the variants into successor branches.

Use a different Codex executable if needed:

```sh
CODEX_BIN=/path/to/codex npm run storyvr:author -- --resource-folder global-migration/captures/active
```

`OPENAI_API_KEY` remains a fallback for proposal and recommendation workflows where Codex CLI is unavailable. Environment panorama and matching-ground generation specifically require a signed-in Codex CLI session and have no API-key fallback. Procedural Dynamics also prefers the signed-in Codex CLI; if generation is unavailable or its result fails validation, StoryVR returns a safe deterministic scene-linked candidate that still requires author review and Apply. If neither Codex nor an API key is available, the generic proposal engine writes deterministic local options so the rest of the UI and compiler remain usable.
