# StoryVR authoring app

This app runs the one-story StoryVR authoring workflow from a prepared resource folder in a sibling story container.

Normalize an existing prepared capture when needed:

```sh
npm run storyvr:story -- --resource-folder ../<story-slug>/captures/active
```

Then launch the authoring UI from that prepared folder:

```sh
npm run storyvr:author -- --resource-folder ../<story-slug>/captures/active
```

Alternative when the story follows the workspace convention:

```sh
npm run storyvr:author -- --story-folder ../<story-slug>
```

The app writes all authoring state into the story container:

- `<story-slug>/analysis/storyvr/project.json`
- `<story-slug>/analysis/storyvr/story-graph.json`
- `<story-slug>/analysis/storyvr/story-canvas-segments.json` (generated semantic progress navigation)
- `<story-slug>/analysis/storyvr/performance-optimization.json`
- `<story-slug>/analysis/storyvr/procedural-dynamics.json`
- `<story-slug>/analysis/storyvr/source-motion-overrides.json`
- `<story-slug>/analysis/storyvr/source-motion-playback.json` (optional declarative shared-timeline contract)
- `<story-slug>/analysis/storyvr/proposals/*.json`
- `<story-slug>/analysis/storyvr/decisions/*.json`
- `<story-slug>/webxr-adaptation/public/environment-enhancement/*` (generated surroundings)
- `<story-slug>/discovery/storyvr-runtime.json`
- `<story-slug>/dist-webxr-adaptation/` (production reader rebuilt by **Build story**)

## Participant workflow

StoryVR uses these eight step labels in the authoring UI, in this order:

1. **Story order**
2. **Place objects**
3. **Set the scene**
4. **Object movement**
5. **Scene changes**
6. **Guide attention**
7. **Reader actions**
8. **Review story**

Select **Finish this step** to complete any top-level step and open the next step automatically. Inside a 3D scene editor, select **Save scene and return** to return to that step's story canvas; this does not complete the top-level step. The final review stays open after completion so you can select **Build story** explicitly.

## Participant terminology

Participant-facing labels, instructions, status messages, and accessible text use one term for each concept. Internal IDs and saved-schema fields remain unchanged for compatibility.

| Meaning | Participant term | Internal or legacy terms retained only in code, schemas, and technical notes |
| --- | --- | --- |
| Narrative unit | **story part** | beat, slide |
| Literal item on the Story order canvas | **card** | beat card |
| Alternative within a story part | **choice** | variant, option |
| 3D state opened from a story part or choice | **scene** | beat scene, variant scene |
| Workflow unit | **step** | checkpoint, stage, component |
| Attention authoring indicator | **focus marker** | attention target, target marker |
| Surrounding world | **setting** or **360° setting** | environment, panorama, background environment |
| Movement within one scene | **object movement** | dynamics, procedural dynamics |
| Change between story parts or choices | **scene change** | transition, inter-beat dynamics |
| What the reader does to continue or choose | **reader action** | interaction, control, policy |
| Scene object enabled for a reader action | **interactive object** | interactable, manipulation target |
| Paired reader controls | **Previous** and **Next** | previous/next variant controls, back/forward |
| Top-level completion action | **Finish this step** | Save checkpoint, Save story order, Finish review |
| 3D sub-editor return action | **Save scene and return** | Close, Save scene |
| Reader build action | **Build story** | Compile, Compile + optimize + build reader |

Use **card** only for a literal Story order card and **scene** only for a 3D state. Technical sections below may use identifiers such as `source-graph`, `beatId`, `variantOptionId`, and `checkpointState` when they describe implementation contracts rather than participant copy.

## Implementation workflow and contracts

1. Prepare one source story folder, usually `../<story-slug>/captures/active`, and normalize it with `storyvr:story` when needed.
2. Start `storyvr:author` with that resource folder.
3. Review and edit **Story order** (`source-graph`).

   Whenever a StoryVR project opens, including an existing story, StoryVR checks for `analysis/storyvr/story-canvas-segments.json`. If the grouping is missing or stale, StoryVR asks the signed-in Codex CLI in the background to organize the saved story into two to seven semantic sections and writes that file; this check does not depend on Source Graph being the currently restored checkpoint. The progress strip remains navigation above one continuous Source Graph canvas: it never filters, groups, rewrites, or recompiles the underlying beat/variant chain. Each section must contain one contiguous beat range, and the sections must cover every authored beat exactly once in story order.

   StoryVR signs both the ordered beat structure and the narrative inputs used for grouping, including titles, text, variants, and explicit arrows. A relevant draft edit immediately marks progress as waiting for save. After the author selects **Finish this step**, StoryVR runs an asynchronous incremental update that supplies the previous sections, a compact complete outline, and detailed context only for changed beats, variants, and their neighbors. Cached current results return without invoking Codex. Concurrent requests for the same saved flow share one job, and a result is committed atomically only if its signature still matches the saved graph. Invalid, stale, failed, or malformed output never changes the story canvas or overwrites the last saved grouping.

4. Compose the story world in order:
   **Place objects** (`spatial-relations`) and **Set the scene** (`environment-enhancement`).

   **Place objects** is the second visible StoryVR step and incorporates the internal `spatial-relations` and legacy `asset-topology` contracts. It opens on a full-width Story canvas rather than a separate topology option workspace. Selecting a story part or choice card opens that card's scene; **Save scene and return** flushes the spatial draft and returns to the canvas. The canvas intentionally has no Asset Library because its scene membership comes from the links already saved in Story order.

   Each scene starts from one deterministic inferred layout containing only the assets linked to that beat or variant. The editor does not generate alternative layout or viewpoint options; authors directly move, rotate, scale, copy, and paste the inferred scene objects. The reader position is represented only by the scene’s concrete Reader transform. Manual changes write concrete transforms into the active scene and participate in the same persistent undo/redo history. There is no separate topology preview or `Active species` view.

   **Set the scene** (`environment-enhancement`) is a Generate-only workflow rather than an AI design-option bundle. It uses the signed-in Codex CLI to create one story-local 2:1 equirectangular LDR `.png` panorama from an editable prompt. Authors can paste, drop, or choose up to four PNG, JPEG, or WebP screenshots and image files as temporary visual references; StoryVR verifies their file signatures and asks Codex to extrapolate their setting, layout, materials, lighting, and mood into the full 360° sphere. Codex also creates a square matching-ground texture from the generated panorama. StoryVR installs the panorama and ground atomically, keeps the panorama unchanged as the surrounding, and uses the generated texture only on the editable world-fixed near-ground movement cue. A generated pair is assigned only to the currently open story scene by default, including the exact choice in a parallel variant group; **Apply to other story scenes…** can reuse that same pair and tuning on an explicit checklist of ordinary or variant scenes without duplicating files or rerunning generation. The implementation stores exact variant-scene settings alongside backward-compatible beat and default assignments, then compiles them into the reader through base-relative runtime paths. An exact variant assignment wins over its host beat and story-wide default, so sibling choices can use different settings; legacy beat-level settings continue to apply to their variants until an exact choice is authored. Unassigned scenes use StoryVR's standard neutral scene, while legacy saved HDR, EXR, and story-wide drafts remain readable but cannot be newly acquired through this step.

   Setting generation keeps a conversation for each exact scene. Follow-ups use the saved panorama and ground as image references together with prior messages, preserving the scene's tuning while revising its imagery. The generated pair and accepted exchange save atomically; failed or stale replies retain the message for retry. Clarifications and replies that leave the setting unchanged save only the conversation and preserve checkpoint and Reader build status. **Clear conversation** resets that scene's chat while keeping its images. Undo restores the conversation; applying an image pair to other scenes does not copy the source chat. Conversation metadata remains in the authoring manifest and is excluded from Reader build signatures. Image-tool failures remain errors even if a worker describes the result as unchanged; only a verified installed image pair receives the Setting ready banner. Conversation-only results use Reply saved or Clarification needed. Generation diagnostics are retained under the current story's `analysis/storyvr/generation-diagnostics/`, including bounded prompts, sanitized invocation arguments, CLI output, and structured worker-reported tool arguments and errors.

   `Spatial Relations` is the canonical `spatial-relations` checkpoint. When the checkpoint first becomes ready, StoryVR infers one default scene for each authored beat and variant, records the inference inputs and confidence, and displays those scene states on the Story Canvas. GLB and image entities are identified by stable source asset plus scene identity rather than transient Three.js UUIDs, GLB node names, or child indexes. Reader text is a hand-attached runtime surface and is not displayed or transformed in this checkpoint.

   Legacy text-panel placement metadata remains readable for older saved projects, but it no longer participates in Spatial Relations rendering, transforms, or travel inference. Asset transforms are scene-scoped additive overrides, so the same linked asset can use a different layout in different beats without rewriting its internal meshes, bones, materials, or animation tracks.

   Captured source-layout evidence is flattened before Spatial Relations inference. The adapter bakes the shared source frame into each GLB's own position, quaternion, and scale, and the editor stores those values as the object's independent inferred transform. No parent entity, grouped hierarchy, attachment state, or shared runtime transform is created. Raw source geometry can retain its loader compatibility policy without being normalized a second time, so inferred relative position, rotation, and size remain unchanged in the editor, **Review story**, and compiled reader. Authors can freely select any combination of those ordinary objects and reset each one to its own inferred baseline.

   The Spatial Relations editor lets the author select the beat-owned Reader pose plus the active scene's linked GLB roots and image planes. In the object list, Shift-click selects a contiguous range and Command/Ctrl-click adds or removes one object; a multi-selection moves, rotates, or scales around one shared center while preserving every member's relative transform. The Reader can move and rotate but cannot scale, so any selection containing the Reader keeps group scaling unavailable; its position and facing are shared by that beat's within-beat variants. A manual Reader edit overrides the live source-camera fallback until Reset restores inference. GLBs and images can move, rotate, or scale with the same viewport gizmos and numeric controls. Manual edits remain distinct from the inferred baseline, support reset-to-inference, and are saved with stable scene-scoped entity IDs. Each asset uses an additive author-transform wrapper outside its normalized and animated content root, so authored placement composes with source clips, shared timelines, material bindings, and later interactions without animation ticks resetting the edit. Spatial Relations v1/v2 authored GLBs migrate to the current floor-contact pivot before their transform is reused; v3 persists that placement basis with cross-scene transform propagation. Final Review and the reader resolve the same per-beat visual-asset and Reader-pose composition used by the checkpoint preview.

   **Build story** emits the current saved `spatialRelations` contract and resolved per-beat/variant scenes into the runtime payload. Loading older projects migrates legacy story-wide GLB transforms into every beat that links the asset, preserves compatible `text-comfort` placement data, and leaves the migrated Spatial Relations decision as a draft for review. The reader retains fallbacks for legacy global Spatial Relations and `textComfort` runtime payloads. Asset Topology remains only as a derived compatibility projection for older downstream consumers; it is not a separate authoring step.

   Shared-timeline anchors are declarative and story-local. An anchor is active by default and needs a normalized `localProgress`; an anchor with `presence: "inactive"` (or `entryMode: "inactive"`) clears that asset without a progress value. A model may opt into floor alignment with `framing.verticalAlignment: "ground"`; omitted framing keeps the existing centered reader placement. This supports sequential shared-timeline assets and later re-initialization without story-name, beat-index, clip-name, or node-name logic in the engine, preview, or reader. Invalid schema versions, asset references, anchors, loop modes, timelines, and clip declarations are returned as nonfatal `sourceMotionPlayback.diagnostics` instead of silently selecting legacy playback.

   Shared-timeline material behavior is also declarative. An asset can declare reusable `materials` recipes such as `texture-background-fade`, `uv-stripe-flow`, `texture-atlas-scalar-field`, or `layered-texture-atlas-scalar-field`, then connect GLB node properties, timeline progress/time, wall-clock time, or constants to recipe uniforms through `material-uniform` bindings. The background-fade recipe mixes an existing texture with a declared background color while a driver controls both texture contribution and opacity. The layered-atlas recipe accepts the atlas column/row counts, sample count, data channel, scalar gain, alpha floor, color ramp, and normalized atlas offset as story-local parameters; `sliceY` selects and interpolates a layer while `showAmt` controls its animated contribution. Static render settings such as sidedness, transparency, depth writing, blending, and render order stay in the story-local recipe. Use `visibility` when a driver should only gate a renderable; reserve `draw-range` for geometry whose index order genuinely represents reveal order. The authoring preview and compiled reader evaluate the same recipe and binding contract.

   Point-cloud companions are likewise optional and declarative. StoryVR activates one only when the imported runtime contains a valid `storyvr-pointcloud-composite-effect/v1` record scoped to `explicit-source-ptcloud-link-only`; a standalone `.pcd` asset does nothing. The shared author/reader loader attaches the PCD only to its explicitly matched GLB, decodes bounded ASCII PCD groups, preserves the captured model-to-cloud transform, and drives each fixed droplet layer from its named source animation node with a timeline fallback. A missing or invalid companion is reported nonfatally and never prevents the GLB or the rest of the story from rendering. Ordinary stories retain their prior runtime, graph, checkpoint, and reader behavior.

5. Review story behavior:
   **Object movement** (`dynamic-geometry`) and **Scene changes** (`inter-beat-dynamics`). These steps do not generate design-option bundles. They can use the latest saved or inferred story, setting, and spatial drafts without requiring earlier steps to be marked finished; final completion and Reader builds still enforce the full current workflow. Object movement opens on a full-width Story canvas containing every authored story part and choice; selecting a card opens the exact saved scene with its story-part-resolved setting, classification evidence, playback controls, and manual motion-link editor. Its Scene objects hierarchy lists the complete saved Reader, GLB, and image roster plus runtime-generated objects, with every animating entry highlighted. The viewport and numeric inspector reuse Place objects' selection, marquee, Move/Rotate/Scale gizmos, W/E/R shortcuts, proportional scale lock, Undo/Redo, and saved-GLB copy/paste. Saved-object adjustments remain canonical Place objects transforms; generated-object adjustments are stored as a Dynamics-local `authorOffset` composed after animation. The reader-hand text system surface is intentionally not materialized in this scene editor.

   In that exact beat or variant scene, the author may describe declarative animation or temporary effects in plain language. Selecting saved GLBs or image planes in the scene makes those exact entities the generation subjects; an empty selection lets Codex derive subjects from the prompt and saved scene, and StoryVR does not auto-select Reader. Existing GLBs and saved image planes are exact-entity motion targets: both support legacy paths and general multi-property timelines with `once`, `repeat`, or `ping-pong` playback, while only GLBs may use embedded clips. Image animation uses temporary outer-root transform offsets plus visibility, opacity, and color tracks, so its saved placement and size remain untouched. A plan may also create beat-local primitives, lights, and particle emitters, so an effects-only scene does not need a placed GLB. Exact-scene PNG, JPEG, and WebP files remain bounded visual attachments in the prompt as well as legal saved image actors. Generated objects are runtime-local and are disposed when the scene ends; Story order, linked assets, saved Spatial Relations, and authored instances remain unchanged.

   Object movement keeps one saved conversation for each exact scene. The first message generates and saves a declarative plan; later messages receive the conversation and accepted plan so concise follow-ups can refine, add, remove, stop, or restore behavior. Codex interprets the complete request, saved scene, and conversation instead of local keyword rules. An exact historical restoration names an accepted assistant snapshot, and StoryVR restores the stored plan itself—including timing, seed, and manual generated-object offsets—after validating the current scene and selection. There is no separate Apply or Discard step. Generation remains read-only until the candidate passes story, spatial, image-reference, asset-inventory, selected-subject, prompt-requirement, action-fidelity, and procedural-revision checks, then one short atomic commit records the turn and any plan update as one persistent Undo action. Selected subjects scope which existing animations may change, while unselected animation remains intact. Clarification or no-visible-change replies may be saved without changing runtime output, and a provider, generation, or save failure leaves the previous conversation and animation visible instead of inventing local fallback motion. Named spatial phrases resolve against exact scene identity, source highlight/reference roles, and bounded semantic aliases. Generated lights, primitives, and particles can attach to and follow that entity's post-loader visible-bounds center; ambiguous or missing references block generation instead of using a guessed reader-relative point. Saved procedural Dynamics is stored separately from animation-probe-derived `sourceDynamics`, can be removed without changing source movement links, and uses the authored reader-start world pose only for effects without an entity attachment. The Author, Final Review, and Reader use the same normalizer and sampler with finite-value, headset-comfort, renderer-resource, visible-pivot, and explicit clip-loop safeguards; author-only conversation history is excluded from Reader output and build signatures.

   **Save scene and return** saves dirty motion-link assignments and direct generated-object transform adjustments, then returns to the same canvas position. Its derived draft refreshes automatically from the saved Source Graph and upstream composition, while **Finish this step** confirms both reviewed source behavior and saved procedural plans; variants retain their host beat's individual non-camera clip assignment rather than introducing a second per-variant source-motion schema. Scene changes uses the same canvas-first workflow and explicit step completion, but its original default and parallel choice cards are read-only. Every internal beat-to-beat and variant-to-variant arrow reports one truthful preview state. A matched source window or motion track shows a text-free looping GLB thumbnail and uses `canScrub: true` with `previewMode: "saved-source"`.

   When there is no saved source mapping, **Auto Interpolation** is available only when the two exact saved Spatial Relations endpoint scenes contain at least one safely matched instance of the same GLB or image whose transform changes. Stable source-instance identity is preferred; asset identity is used only when that asset occurs exactly once at both endpoints and there are no conflicting explicit identities. The edge uses `canAutoInterpolate: true`, `canPreview: true`, and `previewMode: "auto-interpolation"`. Opening it interpolates every matched object's position, quaternion, and scale from the prior beat to the next beat. Objects that exist at only one endpoint dissolve out or in alongside that interpolation, but unmatched-only or transform-identical scenes do not claim the feature. A saved shared-timeline window or mapped per-object motion track always takes precedence over Auto Interpolation.

   Auto Interpolation does not set `canScrub`, create a source-motion assignment or saved-animation thumbnail, or add synthetic lines, rings, spheres, or camera motion. Story-opening, frozen, or missing-endpoint routes remain **No saved scene change** with `previewMode: "none"`. Other exact routes without saved movement or Auto Interpolation retain the truthful **No saved scene change** label but use `canPreview: true` and `previewMode: "sudden-cut"`. Their full editor holds the exact source scene for one second, cuts immediately to the exact destination, and holds that scene for one second, so Play, Restart, and Speed remain available. Every full Scene changes preview uses the same one-second source and destination holds, with any saved, interpolated, or generated animation running between them; story-canvas thumbnails and Reader timing are unchanged. Same-beat variant edges reuse the destination variant's exact mapped Object movement clips without adding unsupported same-beat records to the beat-pair motion-assignment schema. Closing the preview saves dirty host-beat assignments through the existing source-motion API and restores the canvas position. The `inter-beat-dynamics` contract prefers an optional asset-level `source-motion-playback.json` contract: authored beats resolve to inactive, initial, animated, or held states on one source-local timeline, and every coordinated clip—including the declared source camera—is evaluated on one absolute mixer clock. Per-track assignments remain semantic contributor metadata and do not select primary preview playback. Stories without a shared-timeline contract retain the mapped legacy per-track fallback. Manual Source Graph asset-to-beat links remain authoritative for probe inference and later-step invalidation.

   Every exact directed arrow between saved scenes can use the Scene changes natural-language generator, including choice-to-choice arrows within a story part and arrows with saved source movement, a frozen destination, or text-only endpoint scenes. The opened editor mirrors Object movement with a **Scene objects** block for the exact destination scene's saved GLBs and image planes, while intentionally omitting transform controls so both endpoint scenes remain immutable. Selection begins empty; clicking, Shift-clicking, and Command/Ctrl-clicking choose generation subjects, while an empty selection leaves subject resolution to the description. Selected entity IDs scope the current conversation edit, so effects on other objects are preserved. Each boundary retains its own conversation, and follow-up messages revise the latest saved transition. Codex receives immutable endpoint identities, entity metadata, transforms, local asset descriptions, and the verified embedded GLB clip inventory. New conversational transitions use `style: "generated"` with explicit property keyframes, embedded animation bindings, or both in `middle.actions`; neither prompt words nor action names select preset effects. Generated tracks compose visibility, saved-relative position and rotation, scale, material color, and emissive properties with independently generated timing and targets. Author and Reader share the same sampler, and final keyframe values hold until the exact destination endpoint. Existing legacy actions can be retained unchanged, while newly added or revised actions require supported tracks or clip bindings and resolvable targets. Invalid replies receive one contract-repair attempt with the original conversation; provider failures never become keyword-based transition presets. Unsupported requests require clarification instead of an unrelated visual substitute. Saved endpoint transforms remain immutable. Playback begins from the live source Dynamics pose and arrives at the held destination Dynamics pose before its motion resumes. Middle objects and property changes are cleaned up on completion or cancellation, and saved source-motion mappings remain stored even when an exact generated transition overlays them. Sending a message validates and automatically saves the exact-route plan and reply in `analysis/storyvr/procedural-transitions.json`. A changed transition marks only Scene changes as draft and makes later checkpoints stale. Clarifications and replies that preserve the current transition retain checkpoint and Reader build status. **Clear transition and conversation** removes the selected connection's generated plan, conversation, and unsent prompt; Undo restores the plan and conversation together. Other connections keep their own plans and histories, and conversation text stays out of Reader output. Final Review and the managed compiled Reader consume the same middle-action contract; customized Readers missing generated-transition playback, selected-target anchoring, property-track support, or the embedded-clip contract required by their saved plans are blocked before build.

   Embedded clips can loop, play once, or ping-pong while movement and appearance tracks run. Each binding uses an exact GLB entity and verified clip index; playback follows transition progress, so pause and backwards scrubbing reproduce the same pose. Author and Reader suspend competing model playback while the transition owns it. A compatible embedded clip continues from its captured phase and resumes in destination Dynamics; an explicit nonzero clip offset selects a different start time. **Start dynamics at (seconds)** previews different source phases, while path-tangent orientation aligns generated travel with its heading. Generation uses the exact endpoints' effective saved Dynamics, including beat fallback for variants, and rejects a preview when either endpoint's plans change before application.

   **Shared story memory** connects Set the scene, Object movement, and Scene changes generation. Before each request, StoryVR indexes the current saved story into `analysis/storyvr/shared-memory.json`: scene names and order, choice labels, exact object identities and available GLB clips, saved background descriptions, complete Dynamics and transition plans, and recent authoring intent. Authors can refer to saved work naturally—for example, “Use Florida's background here” or “Give these models the opening scene's movement.” Referenced source work stays unchanged, while the requested behavior or visual intent is rebound to the current scene. Ambiguous references produce a clarification rather than a guessed match. The index is derived from authoritative saved artifacts and excluded from Reader builds and authoring-history signatures.

6. Review the reader experience:
   **Guide attention** (`attention-guidance`), **Reader actions** (`interaction-control`), and **Review story** (`transition-pacing`).

   **Guide attention** opens the same story-part-and-choice canvas pattern and can use the latest saved or inferred scene composition without waiting for Scene changes to be marked finished. For each scene, StoryVR independently derives a runtime target set from direct JS/Three.js model, part, animation, and visibility changes and a semantic target set from the saved narrative text, exact Story order links, asset labels, and named-part metadata. Variant runtime evidence remains scoped to the option that produced it; an unavailable capture or a DOM/preload link is not relabeled as direct runtime evidence. Semantic ranking is confidence- and margin-gated so generic text does not silently choose among several plausible GLBs.

   The two channels are reconciled internally as `confirmed`, parent/part `compatible`, provisional `runtime-only` or `semantic-only`, `conflict`, or `unresolved`. One-sided and conflicting results are retained in the inference contract instead of being discarded or silently overridden, while the authoring UI directly accepts the suggested target set without showing channel evidence, reconciliation labels, or a separate review action. Selecting a card loads its composed scene and validates every reconciled candidate against live, nonempty visible GLB geometry before creating an authoring-only **focus marker**. Exact active-part selectors and safe standalone GLBs are supported; automatic inference does not fall back to broad groups, hidden controls, ambiguous shared-timeline models, or camera focus. A scene with no inferred target starts with no focus marker, but the author may explicitly select any visible saved-scene GLB or image plane, including a shared-timeline model, or choose **Place focus marker manually** and click once in the scene to create a free scene-scoped spatial point. The server rejects arbitrary or out-of-scene asset IDs and nonfinite point coordinates. Selecting a focus marker and pressing Delete or Backspace removes it, persists that author choice across scene reloads, and makes an object or manual-position target available to add again; focus markers remain authoring metadata rather than story objects.

   **Build story** removes the authoring focus markers and emits only finite, evaluated attention targets plus a versioned reader cue policy. Until the distance from the active desktop or WebXR viewer to a resolved target's visible bounds first reaches 3 meters, the target receives an animated investigation sparkle and, only while those bounds are outside the active view frustum, a large high-contrast arrow points toward it from well inside the headset's peripheral edge. The compiled policy carries the arrow's screen-space size and inward placement so different headset projections retain the same salient cue. Entering the 3-meter radius permanently completes that target for the current story session: both cues disappear immediately and do not return after the reader moves away, changes story parts or choices, or leaves and re-enters WebXR. The reader resolves saved GLBs, exact parts, and image planes against their visible renderables, computes free-point guidance directly from the saved scene coordinate, and never renders an authoring focus marker or substitutes an origin marker for an invalid or unresolved target.

   Reader actions is proposal-free: it derives its editable boundary structure directly from the current Story order, saved spatial relations, and reviewed scene changes. It opens on a full-width Story canvas that preserves every story part, parallel choice card, and choice link. Selecting a story part or choice card opens its exact scene as an interaction editor. The author can click visible GLB geometry in the scene or use the synchronized target list to mark a whole GLB or its deepest safe named/indexed part as one-hand grabbable, two-hand scalable, or both. Optional parent-local movement, rotation, and scale ranges use simultaneous translucent clones of that exact target: teal is Minimum and orange is Maximum. Clicking either ghost or its matching row activates the gizmo for that endpoint, and movement limits also draw the box between both endpoints.

   The Reader actions preview plays the exact scene's saved Object movement. Direct-manipulation goals use a translucent animated model that keeps unchecked transform channels following the source. **Frame original + target**, **Reset target**, and **Lock ratio** support placement and sizing, with movement-range and position-tolerance guides. **Completion timing** selects immediate matching, a continuous hold within tolerance, or matching followed by releasing every selected object; hold and release modes require manipulation first. Goal edits preserve the camera and support Undo.

   Sequential boundaries with `No mapped scene change` use `Controller button press` by default; mapped scene changes remain `Unassigned` until the author chooses a reader action. `Direct manipulation` is available only when the exact source scene contains at least one authored interactive object, and its destination list contains only those interactive objects. For each selected target, the author chooses one or more completion-trigger components from the transforms that its affordances can produce: position, rotation, scale, or any supported combination. Only those selected components must reach their destinations and remain inside their authored transform ranges; unreachable destinations are marked in the editor. Existing records without an explicit trigger-component list continue to require every affordance-supported component. The controller icon above the Story canvas opens one shared mapping that automatically applies to every current or later `Controller button press` scene change; arrow icons no longer open an individual controller editor. Controller navigation may use face buttons, Menu, thumbstick press, or thumbstick directions. Thumbstick directions additionally expose direction-only VR locomotion actions. By default, Left Up/Down moves continuously forward/backward, Left Left/Right strafes continuously, Right Left/Right turns in 45-degree snaps, Right Up activates free teleport, and Right Down turns back 180 degrees. Locomotion actions cannot be assigned to face buttons, Menu, or thumbstick Press. Trigger and Grip are omitted from the authoring controls; Trigger belongs to the UI-ray interactor for click and scroll, while Grip belongs to panel and scene-object grabbing. Reset restores `Controller button press` on an unmapped boundary and clears the assignment on a mapped boundary. **Save scene and return** keeps the shared controller mapping and any route-local Direct or Reader locomotion assignments, then restores the canvas position; **Finish this step** remains the only persistence boundary and is disabled while a mapped scene change is unassigned or a Direct destination is incomplete. Choices within one story part keep a separate `UI button press` contract and never become narrative branches. **Previous** and **Next** buttons live on the reader's text panel and follow each choice group's saved order and wrap behavior. Text panels follow the reader's hand and never create hidden travel stations. `Reader locomotion` supports physical walking and boundary-driven virtual teleport modes, and older `Embodied progression` records remain readable as the legacy name for that locomotion family. Both modes expose the exact saved destination as a visible floor cue: physical walking advances only after continuous arrival for the saved dwell, while virtual mode advances immediately after either an exact teleport landing or an outside-to-inside head or continuous-movement entry. A reader who starts inside a virtual target must leave and re-enter, preventing a zero-distance route from auto-skipping on scene load.

   In the compiled WebXR reader, the first authored Reader pose establishes story entry. Later separated Reader poses feed explicit physical-walking or virtual-teleport boundaries. Hold Right Up to aim, use the valid/invalid reticle to check the landing point, and release to teleport only when the reticle is valid. When an active virtual-teleport boundary is visible, landing inside that exact target advances the saved route or directed choice once, then applies the authored destination and facing while preserving live headset tracking. A physical-walking target takes precedence over an overlapping virtual target and cannot be completed by teleport. Everywhere else, the same input remains free teleport and never changes the story part. It is limited to the current scene's bounded, flat StoryVR ground plane plus the bounded tolerance area of an active virtual target, so it does not support stairs, multiple levels, arbitrary model surfaces, or unrelated points outside the ground bounds. Thumbstick movement is available throughout the story, including Direct manipulation and Reader locomotion boundaries: it preserves analog strength and diagonals, moves on the horizontal plane relative to live headset yaw, and applies 45-degree snap turns or a 180-degree turn back around the headset rather than the rig origin. The text panel attaches to the left hand by default. Aim at either the expanded panel or its minimized `Aa` state with the other hand, hold that controller's Grip to grab it, and release to attach it to that hand. When the ray is not on the panel, one Grip grabs an authored grabbable target and two Grips scale an authored scalable target; every frame clamps the target to its saved local transform ranges. Authors can opt a one-hand target into Elastic dragging: slow motion stays 1:1, while quick translation along the controller ray receives a smooth gain up to 4× so pulls reel a distant object closer and pushes send it farther away. The gained displacement and its 90 ms inertial response stay on the signed controller-ray axis instead of inheriting sideways hand motion. After easing into the gained velocity, the reader preserves it for as long as Grip remains held; releasing immediately pins the object instead of throwing it. Tracking discontinuities are rejected rather than amplified, and reaching an authored position constraint stops the inertial motion. A Direct transition advances only after its selected interactable destinations satisfy the capability-reachable channels. Trigger is exclusively the UI-ray action: it clicks minimize, restore, and choice buttons, and trigger-drag scrolls overflow panel text. Story parts with choices add **Previous** and **Next** UI buttons to the same panel so the reader can move backward or forward through the choices. Reserved Trigger/Grip gestures cannot execute legacy authored mappings or move the story forward. Outside XR, both the compiled desktop panel and **Review story**'s spatial panel can be repositioned with a mouse; dragging the `Aa` state does not also restore it.

   Use **Review story** to inspect the canonical reader preview composed from all current saved decisions, including the same mouse-drag and WebXR grip-grab behavior for the panel. The preview opens at the authored Reader camera; right-drag looks around transiently, and **Reset view** restores the saved Reader pose without changing authored state or history. Reader actions and Review story resolve Reader locomotion from the exact active boundary, project its cue to the floor while preserving saved Reader height and facing, and advance to the exact destination scene when the preview completes. Add a final tuning prompt when the reader story needs small output adjustments, select **Finish this step**, then select **Build story**. StoryVR starts the build in the background from a stable snapshot, compiles the current decisions into `<story-slug>/discovery/storyvr-runtime.json`, prepares the managed source in `<story-slug>/webxr-adaptation/`, applies the bounded performance profile, and runs the production Vite build into `<story-slug>/dist-webxr-adaptation/`. If authored inputs change while that job is running, StoryVR keeps the previous runtime, source, and production build in place and marks the result as out of date so the author can build again. If a legacy reader has a `tools/build-story-instance.mjs` data generator, StoryVR runs it before Vite. The signed-in Codex CLI analyzes only a bounded summary of the story's renderable workload and selects validated desktop pixel-ratio, antialiasing, shadow, XR framebuffer-scale, and fixed-foveation settings. The applied profile is embedded in the runtime and recorded in `<story-slug>/analysis/storyvr/performance-optimization.json`.

   This pass cannot edit source files, assets, transforms, camera poses, timing, sequencing, text, or interactions. StoryVR clamps every numeric setting to the reader contract before applying it. If Codex is unavailable, unsigned, times out, or returns invalid JSON, the compiled reader remains usable with its existing render defaults and the compiler records a nonfatal diagnostic plus a skipped or failed audit report.

Each editable top-level step has one **Finish this step** action and remains editable after saving. Authors can edit, generate, and autosave steps in any order, using the latest saved drafts and inferred scene data. Switching steps saves pending drafts without requiring the step to be finished. A material upstream edit can mark affected downstream decisions as needing review, but does not lock their editors or draft saves. Final Review completion and Reader builds still require current, valid decisions; scene identity, asset validation, and generation revision checks continue to protect against incompatible edits. Regeneration preserves authored placements and choices. **Place objects**, **Object movement**, **Scene changes**, and **Guide attention** do not generate design-option bundles; Place objects starts each scene from one deterministic inference, while Set the scene's Generate flow creates one paired panorama-and-ground setting.

Interactive preview metadata belongs in a screen-space overlay, not inside the Three.js story scene. Shared previews do not add ground circles, stage discs, halos, or other decorative geometry unless the author explicitly requests that geometry or the selected StoryVR option requires it.

## Undo and redo

StoryVR keeps one chronological authoring history for the current browser session. Use `Command-Z` on macOS or `Ctrl-Z` on Windows/Linux to undo; use `Command-Shift-Z`, `Ctrl-Shift-Z`, or `Ctrl-Y` to redo. The header buttons show the next operation available in each direction. When focus is inside an input, textarea, select, or editable element, the browser's native text undo takes precedence.

History includes draft edits, Story order operations and saves, motion-link saves, generated options, paired panorama-and-ground generation, focus-marker additions, moves, and removals, graph regeneration, and step completions. It excludes navigation, filters, camera and playback controls, authentication, and Build story. Persistent redo restores the exact saved checkpoint rather than rerunning generation. History keeps the latest 50 operations and is cleared by a page reload; its temporary checkpoints are not written into the story folder.

## Optional interaction data collection

The header's **Data collection** switch is off by default. In a current Chrome
browser, turning it on first opens a folder chooser, creates one named
`storyvr-interaction-log/v1` JSON file, and begins recording clicks and selected
3D actions while omitting typed values and sensitive data fields. StoryVR
checkpoints new events into that same file while collection stays on. Turning
the switch off stops new capture at that moment and finalizes the existing file.
Canceling the initial folder choice leaves collection off, while a failed
checkpoint or final save preserves the cutoff and unwritten events for retry.

While collection is on, StoryVR also records one additive
`generativeTokenUsage` summary in the same `storyvr-interaction-log/v1` file.
Counts come directly from Codex CLI and OpenAI provider usage; StoryVR does not
tokenize prompts locally or issue a second measurement request. The summary
uses `storyvr-generative-token-usage/v1`, preserves cumulative counts across
checkpoints without double counting retries or build polling, and never stores
prompts, outputs, credentials, provider response IDs, Codex thread IDs, or
local paths. Older logs without the field remain valid and mean not measured.

Run `npm run storyvr:study-extension` to build the optional consent-gated Chrome
bridge for an approved original-story tab. That page contributes events only
when its exact tab, origin, and path have been approved in the extension popup
and StoryVR's **Data collection** switch is on. See
`tools/storyvr-study-extension/README.md` for installation and privacy limits.

Run `npm run storyvr:workflow` from the standalone repository and open
<http://127.0.0.1:5197/> to inspect exported logs in the StoryVR Session Viewer.
Imports remain local unless **Review current session** is selected; that action
sends Codex a bounded summary instead of the source log.

## AI engine

The preferred provider is the local Codex CLI auth boundary. StoryVR pins every Codex generation command to `gpt-5.6-sol` with `--model`, independently of the user's global Codex model setting. This includes text planning, panorama generation, and matching-ground generation.

Structured text/JSON planning explicitly uses Ultra reasoning and has no StoryVR-imposed time limit. This applies to Dynamics, Scene changes, Story progress, generic proposals, and performance planning; legacy planner timeout options no longer terminate requests. Output-size safeguards remain, and generation errors prioritize Codex's structured failure reason over startup diagnostics. Login, upload, image-generation, and local build timeouts are separate from this planning policy.

Dynamics uses a separate saved conversation for each scene and variant. Each new message receives the conversation and accepted plan, so short follow-ups such as “make it slower” refine existing behavior. The latest message can add, remove, or stop behavior without repeating the original description. Selected objects limit which existing animations may change; animations on unselected objects remain intact. Replies that ask for clarification or make no visible change can be saved without changing the animation or invalidating its build.

Dynamics binds the selected objects to the generated reply through saving and rejects a clarification that changes motion. **Clear animation and conversation** resets the saved motion, chat, and composer together; it also works on scenes with only conversation history. Undo and Redo restore or clear them together, and replies generated before a reset cannot be saved afterward. Clearing only conversation history preserves Reader build status. Successful generation resumes the preview only when its exact scene is still open.

Successful user/assistant turns and accepted plan snapshots are stored in `procedural-dynamics.json` under `conversationsByScene`, atomically with animation updates. Reload and Undo/Redo retain the matching plan and conversation; failed requests leave the existing saved result intact. Existing scenes use their saved animation as the conversation's starting point. Conversation history stays in the editor and is omitted from the Reader export and build-input signatures. The browser clears a sent message only after the result has saved successfully.

StoryVR honors an explicit `CODEX_BIN` first. Otherwise it uses an executable `CODEX_CLI_PATH`, then on macOS the CLI bundled with `/Applications/ChatGPT.app` or `/Applications/Codex.app`, and finally `codex` on `PATH`. This prevents an older standalone installation on `PATH` from taking precedence over the desktop runtime. Restart the StoryVR server after changing its executable or updating its CLI configuration.

- The UI starts `codex login --device-auth`.
- The browser receives only the login URL, device code, and status text; it
  never receives credentials or tokens.
- Codex stores credentials in the local Codex CLI configuration.
- Proposal generation runs `codex exec --json` in read-only mode and asks Codex to return a structured proposal bundle for generated-option checkpoints.
- Source Graph progress generation runs asynchronously in an isolated temporary workspace. Its prompt contains the saved narrative outline and instructs Codex to use only that JSON input; Codex returns section ids, labels, and beat ids, while StoryVR supplies signatures and provenance after deterministic validation.
- Final compilation runs a separate read-only Codex performance-planning request after the runtime and reader source are prepared. The response is a small renderer profile, not code; StoryVR validates it, writes an audit artifact, and applies the profile through the compiled runtime.
- `Dynamics` and `Transition` continue to expose animation-probe judgments from the Source Graph rather than generating design-option bundles. Dynamics additionally accepts scene-scoped declarative timelines and runtime-created primitives, lights, and particles; conversational messages validate and save them automatically. Transition accepts an open-ended declarative middle sequence on any exact directed scene arrow, including choices within the same story part, while enforcing exact saved endpoints; conversational messages validate and save updates automatically, with prior effects retained unless the message changes them. Executable code, shaders, external URLs, and arbitrary runtime property access remain prohibited.
- `Environment Enhancement` uses the signed-in Codex CLI to create a 2:1 equirectangular LDR PNG from the author's editable prompt, then uses that panorama as the visual reference for a square matching-ground texture. Generation affects only the exact open story scene, including a selected variant; the author can explicitly apply the installed pair to any checklist of other ordinary or variant scenes. Reference-image review, deterministic generated-asset validation, prompt review, scene assignment, and final checkpoint save remain separate author-controlled actions.
- `Spatial Relations` infers an editable transform baseline from the complete saved story graph and the actual preview geometry. Semantic evidence selects anchors and coordinate spaces; beat-scoped topology generation proposes layout families using only that scene's saved links, and deterministic geometric evaluation materializes their numeric transforms. It does not accept client-supplied asset IDs or ask an AI response to invent unchecked story-specific meter values.
- `Attention Guidance` derives narrow candidate links from the saved Source Graph, lets authors add any visibly rendered scene model or image as a target, and supports one free target placed directly in the scene. The loaded preview confirms finite object positions, while unresolved candidates stay separate from confirmed markers and never become zero-position placeholders.
- `Interaction Control` records hand-attached text panels as reader-relative system surfaces, so obsolete world-, asset-, or source-focus panel transforms cannot infer locomotion. Reader locomotion requires a separate explicit spatial route rather than hidden text-panel placement.
- Beats with preserved within-beat variant groups receive a separate `UI button press` Interaction Control record. The compiled reader renders previous and next controls on the text panel and swaps variant text/assets without advancing the narrative beat or turning the variants into successor branches.

Use a different Codex executable if needed:

```sh
CODEX_BIN=/path/to/codex npm run storyvr:author -- --resource-folder ../<story-slug>/captures/active
```

`OPENAI_API_KEY` remains a fallback for generic proposal workflows where Codex CLI is unavailable. Environment panorama and matching-ground generation specifically require a signed-in Codex CLI session and have no API-key fallback. Procedural Dynamics and conversational Transition generation require the signed-in Codex CLI and surface provider or validation errors while retaining the message for retry. Legacy non-conversational Transition API calls retain their deterministic preview fallback. If neither Codex nor an API key is available, the generic proposal engine writes deterministic local options so the rest of the UI and compiler remain usable.
